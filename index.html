About

From the first test case
to the release sign-off.

Eight years, three products, and the same job each time — someone had to own quality and nobody did. I've written the first test case, built the framework it runs in, hired the team that maintains it, and made the call on whether we ship. Most of what I know came from building it wrong first and then having to fix it in production. Three things I'd argue for in any team I join:

◎

Assert data, not pixels

Charts and dashboards get validated by intercepting the payload behind the visual — not by screenshotting it. Removes an entire class of brittle tests.

compare_screenshot(chart, baseline.png)
expect_response("**/api/metrics") → assert body
⚙

Kill flakiness at the source

Test data goes through the API, not the UI. Most flakiness is a setup problem wearing a timing costume — waits and retries only hide it.

click through 9 screens, then sleep(3)
api.seed_campaign(state="live") in a fixture
◫

Automate what pays

Not everything deserves automation. Knowing where coverage earns its maintenance cost — and where exploratory testing finds more — is the actual skill.

automate every edge case, maintain forever
automate the regression path, explore the rest

Engage — an app built to be hard to test.

A customer engagement platform and the automation framework that tests it — both built from scratch, both public. The app is deliberately awkward in the ways real products are: asynchronous sends you have to poll for, idempotent webhooks, delivery receipts that arrive out of order.

Scope built from zero

8 modules · 43 endpoints · 11 tables. Auth, contacts, segments, campaigns, onsite notifications, surveys, delivery and webhooks, analytics.

Two tenants, one database isolation

Separated through a single scoping helper rather than a filter repeated on every query — so the attack surface is one function, not forty-three endpoints.

Deliberately hard to automate the point of it

An async send returning 202 with work still queued, so tests must poll rather than sleep. Webhook idempotency enforced by a database constraint rather than hoped for in code. Out-of-order delivery receipts that must not regress state. A rules engine with frequency capping measured in a rolling window. You cannot force any of this on a public demo site you don't own.

Testability designed in shift-left

data-testid on every interactive element, and three guarded test-support endpoints that fail closed when unconfigured — the affordances a QA lead should be asking a dev team for.

Seed data down to the epoch determinism

Every id and timestamp is fixed. One table is deliberately left empty, because frequency capping counts in a rolling window from now — a seeded row would age and break reproducibility.

Verified against real Postgres 65 checks

Two standalone verification scripts — 26 and 39 assertions — run against a live managed database, not SQLite.

Postgres everywhere, never SQLite trade-off

LIKE case-sensitivity and sequence behaviour differ between them, and both bugs are invisible until deploy. The cost: local runs cross the network and are ~10× slower than CI.

Free instance — the first load takes about a minute while it wakes. That note is deliberate: a blank screen makes a visitor think you shipped something broken.

The suite green at -n 4

151 tests — 75 functional API, 24 contract, 24 Playwright over page and component objects, 16 Gherkin journeys, 7 that test the framework's own safety guard, and 5 read-only database checks. Green at four-way parallelism in under four minutes. 55 are marked read-only and proven to create and mutate nothing, which is what lets them run nightly against the live demo.

Contract tests that can actually fail proven

FastAPI generates its schema from the same models it serialises with, so conformance mostly proves the app agrees with itself. I tested that: renaming a field left plain conformance green. Mine declare what the consumer needs.

Error states forced, not waited for interception

Route interception produces the 500s, hangs and malformed payloads the app won't produce on demand. Every assertion is that the UI says something — a blank table is worse than an error, because the reader concludes there's no data rather than that something broke.

Payload, not pixels analytics

Charts are asserted by intercepting the response and comparing it to the rendered text. No bar geometry is measured anywhere — I'm testing the transformation, not the chart library.

Parallel-safe by design 4 workers

Session-scoped reset under a cross-worker file lock, cohort-tagged data, and every assertion relative rather than an absolute count — the single most common reason a serially-green suite fails at -n 4.

Service Object Model architecture

Over httpx with typed Pydantic responses the tests own themselves, token caching per identity, and every request/response pair attached to the report with credentials redacted. You read a failure instead of reproducing it.

Guards against silent success three of them

Zero tests collected exits green, so a hook makes it fail. Config drift between the two repos gets named in plain language. And a stale report is caught by comparing what it contains against what the results hold.

Printing a number isn't a control — someone still has to compare it, and they've already decided the run went fine. It has to return a verdict.

Three CI workflows automation

A gate on every push that publishes Allure even when red, a nightly reset of the public demo at 00:00 UTC, and a read-only run against it thirty minutes later that doubles as an uptime check.

Gherkin at the right altitude BDD

Scenarios in the language of the product, not the page. Reaching everyone but leaving the campaign running fails separately from reporting sent having reached nobody — two different defects, two different assertions.

No rerun plugin, on purpose policy

Removing the cheap escape means an intermittent failure must be diagnosed rather than retried away. The cost is that one flake stops the world. It has done so twice, and both times it was a real defect.

Five database tests, and the argument against them read-only

The suite speaks HTTP by default. Five checks are allowed below it, and each one must state in its docstring why the API cannot see the failure — enforced at collection, so a test without that justification aborts the run rather than being merged. Read-only is guaranteed by Postgres, not by convention: every statement runs inside a BEGIN READ ONLY transaction, proven by a DELETE that the database refuses.

They exist because three tables carry a tenant stamp the API never exposes, so a delivery written against the wrong tenant is invisible to every HTTP test and would surface later as one organisation's analytics counting another's sends. The case against is in the pull request too: these tests know the schema, and a schema isn't a contract — a rename that breaks no client turns them red. The alternative wasn't testing it better; it was not testing it.

When the fix was worse than the hole the read-only leak

Read-only lives in the transaction, not the connection — so with autocommit on, the setting reverted between statements and the guarantee was thinner than claimed. The obvious fix, promoting it to a session-level setting, closed the hole and opened a far worse one: the connection pooler hands those same server connections back to the application, which began serving requests in read-only sessions. /api/test/reset started returning 500 — the test framework had silently made the system under test unable to write.

Reverted, then the pool was drained deliberately — 25 connections held open and reset one by one — and cleanliness proven on 20 fresh ones rather than assumed. The real fix was encapsulation, not configuration: the read-only handle is private and the database object exposes reads only, so no caller is ever given a connection it could flip. A test framework that can quietly break the thing it is testing is a worse defect than the gap it was closing.

A guard, not just a defect report DEF-005

Chasing a broken local database surfaced something worse than the outage: make all resets whatever the app is pointed at, and nothing stopped that being production. One wrong connection string and a full run would wipe the live demo.

So the app's health endpoint now reports its database label — enough to recognise, useless for reaching — and the reset fixture refuses to run against it, with a deliberate documented override. Seven tests cover the guard itself, including the case that actually bites: localhost, green health, production behind it. A defect report doesn't prevent the defect.

A defect found in the framework itself DEF-003

A wait that always succeeded, because it watched an attribute that survived the page change — so every assertion after a navigation could read the previous page and pass. A wait that cannot fail is worse than no wait, because it manufactures confidence. Rated High, fixed, and written up like any other defect.

A CI flake that turned out to be a real defect DEF-001 / 004 — closed

An intermittent red gate survived a keep-alive fix and a retry policy before diagnostics finally named the request: fixture cleanup hitting an unhandled integrity error already filed as a cosmetic Medium. Under CI's request density the connection was reset mid-response, and because it ran in teardown it failed a test that had already passed.

Re-rated High on its own evidence, then fixed. Deleting a contact with delivery history now returns 409 with a message that says why, instead of a bare 500. The regression test was watched failing before the fix and passing after — a regression test never seen red isn't one. Both defects closed; the report keeps the Medium → High history, because the re-rating is the lesson.
