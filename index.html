About

Automation depth, with the judgment
to know when not to automate.

Eight years across AI-native SaaS, consumer mobile, and enterprise CRM/CLM. I've been the first QA hire twice and the sole release gatekeeper once — which means most of what I know came from building it wrong first, then fixing it. Three things I'd argue for in any team I join:

◎

Assert data, not pixels

Charts and dashboards get validated by intercepting the payload behind the visual — not by screenshotting it. Removes an entire class of brittle tests.

compare_screenshot(chart, baseline.png)
expect_response("**/api/metrics") → assert body
⚙

Kill flakiness at the source

Test data goes through the API, not the UI. Most flakiness is a setup problem wearing a timing costume — waits and retries only hide it.

click through 9 screens, then sleep(3)
api.seed_campaign(state="live") in a fixture
◫

Automate what pays

Not everything deserves automation. Knowing where coverage earns its maintenance cost — and where exploratory testing finds more — is the actual skill.

automate every edge case, maintain forever
automate the regression path, explore the rest

Portfolio project

Engage — an app built to be hard to test.

A customer engagement platform and the automation framework that tests it — both built from scratch, both public. The app is deliberately awkward in the ways real products are: asynchronous sends you have to poll for, idempotent webhooks, delivery receipts that arrive out of order.

Engage — application under test

Live

Python · FastAPI · SQLAlchemy · PostgreSQL · Vanilla JS · Vite

  • 8 modules, 43 endpoints, 11 tables — auth, contacts, segments, campaigns, onsite notifications, surveys, delivery and webhooks, analytics. Two tenants sharing one database, isolated through a single scoping helper rather than a filter repeated on every query.
  • Deliberately hard to automate — async send returning 202 with work still queued, webhook idempotency enforced by a database constraint rather than hoped for in code, out-of-order delivery receipts that must not regress state, and a rules engine with frequency capping measured in a rolling window.
  • Testability designed in — data-testid on every interactive element, three guarded test-support endpoints that fail closed when unconfigured, and seed data deterministic down to a fixed epoch. One table is deliberately left empty, because its meaning depends on the current time.
  • 65 verification checks passing against real managed Postgres.

Test Automation Framework

CI green

Python · pytest · Playwright · httpx · Pydantic · pytest-xdist · Allure · GitHub Actions

  • 138 tests — 74 functional API, 24 contract, 24 Playwright over page and component objects, 16 Gherkin journeys. Green at four-way parallelism. 55 are marked read-only and proven to create and mutate nothing, which is what lets them run nightly against the live demo.
  • Contract tests that aren't tautological — FastAPI generates its schema from the same models it serialises with, so validating one against the other mostly proves the app agrees with itself. I tested that claim: renaming a field left plain conformance green. These declare what the consumer depends on instead, so a rename or a widened enum fails once, by name.
  • Error states forced, not waited for — request interception produces the 500s, hangs and malformed payloads the app won't produce on demand, and every assertion is that the UI says something: a blank table is worse than an error, because the reader concludes there's no data rather than that something broke.
  • Charts asserted on payload, not pixels — analytics tests intercept the response and compare it to what the page rendered. No bar geometry is measured anywhere.
  • Parallel-safe by design — session-scoped reset under a cross-worker file lock, UUID-stamped test data, and every assertion relative so concurrent workers can't collide.
  • Service Object Model over httpx with typed Pydantic responses, token caching per identity, and request/response pairs attached to every Allure result with credentials redacted.
  • Guards against silent success — a collection hook that fails the run when a selector deselects everything, and a precondition that detects config drift between the app and the suite.
  • Three CI workflows — a gate on every push publishing Allure reports even when red, a nightly reset of the public demo, and a read-only smoke run against it half an hour later that doubles as an uptime check.
  • Gherkin at the right altitude — scenarios written in the language of the product, not the page. Reaching everyone but leaving the campaign running fails separately from reporting sent having reached nobody, because those are two different defects.
  • A defect found in the framework itself — a wait that always succeeded, because it watched an attribute that survived the page change. Every assertion after a navigation could read the previous page and pass. A wait that cannot fail is worse than no wait, because it manufactures confidence. Rated High and fixed.
  • No rerun plugin, on purpose — removing the cheap escape means an intermittent failure has to be diagnosed rather than retried away. The cost is that one flake stops the world. It has done so twice, and both times it was a real defect.
  • A CI flake that turned out to be a real defect — an intermittent red gate survived a keep-alive fix and a retry policy before diagnostics named the request: fixture cleanup hitting an unhandled integrity error already filed as a cosmetic Medium. Under CI's request density the connection was reset mid-response, and because it ran in teardown it failed a test that had already passed. Re-rated High on its own evidence. Cleanup is now best-effort; the application defect stays open, so the fix belongs to the code that owns it rather than deleting the evidence.

SEV-1

INC-2291 — Duplicate push delivery on webhook retry

42,800users affected
18 mintime to detect
51 mintime to mitigate
3client escalations
Summary
A campaign delivery webhook was retried by the upstream provider after a gateway timeout. Because the consumer keyed deduplication on campaign_id rather than delivery_id, the retry was treated as a fresh dispatch and the entire audience received the push a second time.
Blast radius
42,800 end users across 3 enterprise accounts, one of which had a contractual frequency cap of one push per user per day. Reputational, not financial — but a contract-breaching event for that account.
Detection
Not caught by the suite. Flagged by a delivery-volume anomaly alert 18 minutes in, after a client had already noticed.
Reproduction
Deterministic once understood: dispatch a campaign, force a 504 on the provider callback, allow the provider's retry, then compare delivery_receipts count against audience size. Ratio is 2:1.
Root cause
The idempotency check existed but used the wrong key. campaign_id is stable across retries by design, so every retry looked like a legitimate new send. The bug was in the semantics of the key, not in the presence of the guard — which is exactly why code review missed it too.
Why testing
missed it
This is the part that mattered more than the fix. Our webhook tests asserted the happy path and the failure path, but never the retry path — we had no test that delivered the same payload twice. Idempotency was assumed rather than verified, across every consumer we owned, not just this one.
Containment
Paused the affected campaigns, suppressed re-delivery at the gateway, and notified the three accounts before their end-of-day reporting ran — ahead of them asking.
Fix
Deduplication re-keyed to delivery_id, with a persisted idempotency record and a TTL matched to the provider's maximum retry window.
Coverage
added
  1. Duplicate-payload test for every webhook consumer, not just this one — same payload twice, assert exactly one side effect
  2. Contract test asserting the idempotency key is the per-delivery identifier, so a future rename fails loudly
  3. Delivery-count invariant added to the campaign regression pack: receipts must equal audience size
Severity vs
priority
SEV-1 because it breached a contractual delivery guarantee and users could not opt out of the second message. P0 because the retry window meant it could recur on any campaign at any time. Severity describes the damage; priority describes the urgency — keeping them separate is what stops triage becoming a negotiation.
Follow-ups
Idempotency added to the definition of done for any new webhook consumer, and a standing agenda item in design review. The single-incident fix is cheap; the class of bug is what you actually want to close.
