Assert data, not pixels

Charts and dashboards get validated by intercepting the API payload behind the visual — not by screenshotting it. It removes an entire class of brittle tests.

⚙

Kill flakiness at the source

Test data goes through the API, not the UI. Most flakiness is a setup problem wearing a timing costume — waits and retries only hide it.

◫

Automate what pays

Not everything deserves automation. Knowing where coverage earns its maintenance cost — and where exploratory testing finds more — is the actual skill.

SEV-2

BUG-1042 — Cart total ignores promo code after quantity change

Environment
Web · Chrome 128 / Safari 17 · Staging build 4.12.3
Preconditions
User is logged in with an active cart and a valid 10% promo code applied.
Steps
  1. Add any item to the cart
  2. Apply promo code SAVE10 — total updates correctly
  3. Increase the item quantity from 1 to 2
  4. Observe the order summary
Expected
Discount recalculates against the new subtotal; total reflects 10% off the updated amount.
Actual
Subtotal updates but the discount stays pinned to the original single-item value. Customer is undercharged on every quantity increase.
Evidence
Screen recording, HAR file, and POST /api/cart/recalculate response showing discount_amount unchanged while subtotal increments.
Severity
SEV-2 — direct revenue impact, no data loss, no workaround available to the user.
Priority
P1 — affects every promo-code order; ship-blocking for the current release.
Notes
Severity and priority are deliberately separate. Severity is what the bug does; priority is how soon we act. Conflating them is the most common reason triage meetings run long.
